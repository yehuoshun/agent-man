# 决定记录

只记"为什么这么选"。每条固定三段：**决定** / **来由** / **代价**——只写"选了什么"没有价值，
回溯时真正要找的是当时舍弃了什么。

## 账本不做删行 API，`TRACE_KEEP_MONTHS` 只留给将来的清理

**决定**
`state/trace-<月>.jsonl` 只追加，全仓不提供任何删行、截断、覆盖写的接口——没有
`digest.trace.prune()`，也没有 `audit.trace --keep` 之类的开关。`TRACE_KEEP_MONTHS = 12`
（`src/core/const.mjs`）只是一个写在常数表里的保留上限：它没有任何调用方，读取路径也不看它。
`audit trace` 每次都把分片全扫一遍，按 `at` 倒序取 `limit` 条，裁不裁与它无关。

**来由**
1. 审计的用处是"事后还能看全"。design §6 把 `audit trace` 定位成账本读取口，它的价值恰恰在
   时间越久越能回答"上一次为什么丢了这条"。删掉旧月分片，等于把唯一的追责线索交给一个默认值。
2. 删行会同时砸掉两条硬承诺（AGENTS 二）。账本记的是"我做过什么"，改写或删除历史行之后，
   剩下的行不再能证明"没发生过的事"确实没发生——不静默的原则在这里是回溯性质，不是展示性质。
3. 写入只有一条路：`appendJsonl()`（open → write → fsync → close，写完读回自己那一行）。
   这个形状天然没有"改一行"的位置。加一个删行接口，就要在 store 层开第二个写入口，
   而第二个写入口一旦存在，早晚会被别的模块借去改别的行。
4. 现在也不需要它：账本一个月一个文件，二十条记录一屏就用完了，磁盘和读取耗时都还没到值得
   为它引入破坏性操作的地步。清理是"将来 prun 的事"，不是这一版的事。

**代价**
- 账本只增不减。真按每天几十条跑十年，`state/` 下会攒下上百个分片，`audit trace` 的全扫会
  从毫秒级走到几十毫秒级；到那时要么加索引，要么才真的需要 prun。
- 磁盘占用没有任何上限兜底，出问题时不能用一个参数把空间救回来，只能人工删文件——而人工删
  文件绕过了这门语言的规则，删掉的东西也不会留痕（这正是我们不肯写进代码的原因）。
- 将来真要清理，得单独写一个小工具并配一份新决定：清理窗口一旦短于审计需要的窗口，
  `TRACE_KEEP_MONTHS` 就从"没用上的常数"变成"沉默的时限"，到那时这条决定的来由 1 必须被重新讨论。

## 配置只有一份真源，依赖方向不为它开例外

**决定**
`src/core/config.mjs` 是配置的唯一真源：默认值、优先级、校验、写回都在它里面。CLI 只把 `ctx`
递进去，各领域模块读到的配置由入口一次性 `load()` 后传下来。核心层为此自带了两份小工具——
`writeTextAtomic()` 与数据目录解析——**与 `src/store` 的同名逻辑重复**，而不是让 core 反过来
import store。

**来由**
1. §7 的依赖是单向的：`store → core`。让 core import store 会把箭头倒过来，结构用例会红，
   也会让"core 不认识存储布局"这条边界失效。
2. 配置必须在 store 存在之前可用：`AGENT_MAN_HOME` 决定数据目录，而配置本身又要能改数据目录
   之外的默认值。互相依赖的两件事只能挑一边当下层，选 core。
3. 两份实现都在注释里点了对方的名字，并且有 `config path` 的用例把两条路径锁成同一口径——
   重复是明写的，不是抄漏的。

**代价**
- 退避参数（EPERM/EBUSY/EACCES、6 次、15→225ms）现在有两份。改一处忘另一处，会得到"写配置稳、
  写账本不稳"这种只在 Windows 上偶发的怪现象。
- 将来若真要把 `home()` 与 `writeAtomic()` 下移到 core，得同时改 store 与 config 两处调用，
  并重跑全部用例；这版不做，因为 1.0 之前动地基的收益太小。

## 配置迁移只回落默认，不自动写回

**决定**
读配置时缺键自动回落默认值、`version` 不匹配只警告，**不把补好的默认值写回文件**；只有
`config set` / `config reset` 才写盘，写的永远是 `version: 1`。

**来由**
1. 读命令不许有副作用：`config show` / `get` / `doctor` 都会读配置。如果读的时候顺手补默认值，
   一个只读的排查动作就改了用户的文件。
2. 文件里没写的键，语义上就是"用默认值"。补写进去会把"人没表过态"变成"人选择过这个值"，
   以后想改默认值也改不动了。
3. 回落默认让用户永远拿到一份完整的配置，警告让他知道文件和程序版本对不上——两件事分开说，
   比静默修复诚实。

**代价**
- `config show` 必须用 `~` 标出"这是默认值不是文件里写的"，否则人分不清哪几行是他自己定的
  （渲染已有用例锁）。
- 老文件会一直缺键。想让它变完整，得显式跑一次 `config set <键> <值>` 或 `config reset`。

## 结构用例的债务名单只许变短

**决定**
`test/structure.test.mjs` 里立了两条规矩：`process.env` 只准出现在 `src/core/config.mjs` 与
`bin/`；`config.json` / `meta.json` 字面量只准出现在 `src/store/paths.mjs`。规矩落地时已有的
违规不为改它们而停下，记进 `ENV_DEBT` / `META_DEBT` 两张名单，用例只断言"名单不增长"。

**来由**
1. 立规矩的时机不是重写别人的时候：改 `src/parts` 的环境读取属于另一条车道，混进来会让一次
   提交同时改三件事。
2. "只许变短"把债务变成可验证的量：新代码想走捷径，用例当场红；旧账什么时候还，看名单长度
   就知道。

**代价**
- 名单是一份人工维护的清单，删条目时要和实际代码一起改，否则会出现"用例绿但其实还有违规"。
- 有些人会把它当成许可证（"反正名单里有"），所以每条都写了"立规矩时的旧账"。

## 心境网格的分界围着基线排，而不是四等分

**决定**
愉悦分界 `V_EDGES = [68, 50, 33]`、精力分界 `E_EDGES = [76, 58, 29]`，边界归上档；16 宫格的
第 2 行第 2 格是「平淡」、第 3 格是「轻松」。`moodOf()` 只由 `(v, e)` 决定，没有任何"贴着基线
就算平淡"的特例。

**来由**
四等分（`[65,50,35]` / `[75,50,25]`）会让基线 `(50, 60)` 落进「中低 × 中」= 不安。而基线正是
"什么都没发生"的状态：一觉醒来、一句话没说，情绪标签却写着不安——这是设计错误，不是实现错误。
把分界挪成围着 `(50, 60)` 排之后，基线那格天然就是平淡，§14.8 里"(52,61) 恒为平淡"这条例子
不需要任何特例就成立。16 个词一个没换。

**代价**
分界不再等距（愉悦侧 18/17/16 分，精力侧 30/29/29 分），读表的人第一眼会觉得不整齐；
以后想改某一格的边界，得同时考虑基线落在哪一格，不能只看数字。

## 情绪叠加用 log-sum-exp 滚动，不是把刺激直接求和

**决定**
`agg = mergeOffset(decayOffset(agg, dt, axis), weight)`：每条刺激先按半衰期衰减到当下，
再用 `merge(a,b) = ln(e^a + e^b)` 合成一个偏移量，最后 `effective = clamp(baseline + agg, 0, 100)`。

**来由**
直接求和（`baseline + Σ decay(stim)`）在长会话里会饱和：100 条 −8 的失败在 24 小时后仍剩 −150，
愉悦被钉死在地板，之后任何正向事件都拉不回来，而人不是这样——同样的坏事重复十次，
感受增长的是对数，不是线性。LSE 让同类叠加有上限（3 次同级 ≈1.1 倍），
`100×−8` 之后 24 小时回到 ±3 以内，与"情绪会自己走回来"这件事一致。

**代价**
LSE 不满足可加性，单条刺激的贡献取决于同时还有多少条（`persistent()` 的 why 里这句话说不出口）；
想解释某个数字，必须把当时的刺激序列一起给出来，单看一条算不出来。

## 瞬时情绪六类这一版不启用

**决定**
§14.3 的六类词表（惊讶/愤怒/委屈/尴尬/愧疚/感动）留着，但 `transient()` 只报最近 45 分钟内的
刺激（kind / why / at / 剩余比例），**不给它们起情绪名字**。

**来由**
现有十个刺激 kind 到六类之间没有一张确定的对照表：`task.fail` 该算愤怒、委屈还是沮丧，说不清。
硬编一张表等于把我对人的判断塞进脚本，而且表一旦错了，屏幕上会出现一个没人能解释的"愤怒"。
宁可先说"最近 45 分钟有 3 条刺激，两条是失败"，也不要给一个假的情绪名。

**代价**
屏幕上少一层"它现在是什么心情"的表达；启用条件写进了 §14.3——先有真实对话样本，再定表。

## 1.0 之前明确不做的四件事（都是债务，不是漏做）

**决定**
这四条在 1.0 里**明确拒绝**而不是半实现：①`memory add|revise --from 日期..日期`（证据区间）；
②`context digest --due`（只巩固到期项）；③`affect stim --imp`（刺激强度参与权重）；
④CLI 里那几处"长表单行"的排版（`memory show` 的证据/版本行、`audit trace` 的每条抬头、
`affect why` 的峰值与覆盖到期）**就留在 CLI**，不补 view 渲染器。

**来由**
①区间证据要"日期→事件 id"的解析，那是记忆层的事；放进 CLI 就等于把证据解析搬出记忆层，
同一件事以后会有两个口径。②到期过滤是欠账口径的一部分（§14.9 的 debt 三档），
digest 侧还没接 `watermark`，先做过滤只会给出错的"到期"判断。③权重表现在按 kind 定，
让 `--imp` 再乘一道，等于同一件事有两个强度旋钮，谁也说不清最终是几。
④view 的职责是"一屏"：段落短行、段与段之间留白。证据清单、账本行是给复核的人读的表，
不是给模型看的一屏，它们没有第二个读者——为它们造渲染器只是把 CLI 的排版换个地方放。

**代价**
①用户想按"最近一周"给证据，现在得自己查 id（`event ls` 或 `event find`）；
②想只在欠账够多时才巩固，只能靠 `context cue` 的判决，不能手动强制；
③刺激强度只能靠 kind 选对；
④换前端（比如以后做 TUI）时，这四处排版要重写一遍。四条都写进 design §6 的"未启用"。
## 宿主层：装配是纯函数，取数才碰环境

**决定**
`src/host/inject.mjs` 的 `compose({ blocks, budget })` 只收"已经算好的块"，不读文件、不认识 DSH；
真正的取数在 `dsh/index.mjs`（拿 `sessionQuery`、问 `soul` 当前指针、调 `mind.situation`）。
`user` 槽位这一版留空。

**来由**
DSH 运行时只在实机里，`node --test` 摸不到它。把装配拆成纯函数，预算怎么让位、块怎么排、
`used` 是否真等于 `cost(text)` 才能被用例钉住；剩下那层薄适配坏掉的概率低，坏了也在会话里看得见。
`user` 留空是因为称呼已经由灵魂卡的 `[称呼]` 行承担，再写一段画像就是第二份灵魂。

**代价**
`dsh/index.mjs` 的取数路径（`extractNeedles`、`search` 的形状）没有测试覆盖，只能实机验。

## 写情景就记账，巩固完就结账

**决定**
`event add`（CLI 与宿主工具两条入口）成功后调 `mind.debt.bump({ at, imp })`；
`digest.run` 写完账本后调 `mind.debt.settle({ at })`。两处失败都不影响主流程，只用 `! ` 说出来。

**来由**
`debt.unconsolidated` / `unreflected` 是 `context cue` 判断"该巩固了"的唯一计数器，
而这两个数住在 `meta.json` 里、只有 `bump` 会加、只有 `settle` 会清。此前**全仓没有任何调用方**——
门槛永远到不了，于是开口判决只剩下"距上次说话多久"这一条，等于把设计里最要紧的一条判据接空了。
bump 不放在 `memory/` 里，是因为那会让记忆层反向依赖 mind；放在两个入口各一次，是这份依赖方向的代价。

**代价**
两个入口各记一次账，将来加第三个写入口时容易漏；漏了不会报错，只会让门槛慢慢失效。
用例只锁了宿主那一条（`写情景顺手记欠账：记完一条 imp=2 的事，欠账就是 2 imp / 1 条`），
CLI 那条靠 `event add` 的用例间接盯。

## `host.firstStepRecall` 删掉：同一笔钱不能有两个数

**决定**
配置里只留 `inject.{soul,user,situation,recall,total}` 五格，`host.firstStepRecall` 与
`HOST_FIRST_STEP_RECALL` 常数一起删掉。

**来由**
`host.firstStepRecall = 250` 与 `inject.recall = 150` 说的是同一笔预算（首步那一次回顾），
两个键同时存在时，读代码的人必须去实现里猜哪个真的生效，改配置的人两个都可能改。
配置的用处是"一处改、处处生效"，不是"多一个可以互相打架的旋钮"。

**代价**
旧配置里写过 `host.firstStepRecall` 的用户会发现它不生效（`config` 会把它当未知键报出来）；
如果有人真的想要"首步回顾比平时多"，现在只能改 `inject.recall` 这一处。

## 日界只有一个解释器：分片名、号、自我块都听 `clock.dayStart`

**决定**
"今天从几点算起"只由 `core/time.dayKey(ts, { dayStart })` 决定，配置里是 `clock.dayStart`
（默认 `04:00`）。三个落点都把它传进去：事件分片名（`store/paths.eventsFile`）、
id 里的日期（`store/ids.claim`）、自我块的 `## 日期` 段（`memory/self.appendSelf`）。
CLI 与宿主层各在写入口读一次配置交给它们，中间层不许自己算。

**来由**
这个键在 §15 里躺了很久，但没人消费它——所有日期都按 00:00 切。凌晨两点记下的事于是有两种处境：
配了 `04:00` 的人以为"今天"还没开始，屏幕上也确实按 `04:00` 说话，可 id 与分片名都写成新的一天。
一份数据顶着两个日期，读的人只能猜哪个算数；真出问题时，猜错一次就是一个"找不到的记忆"。
宁可把日界一路传到底（改 6 个调用点），也不要留两个各说各话的日期。

**代价**
升级后，凌晨 00:00–04:00 之间写的事件会落进**前一天**的分片，id 日期也跟着变；旧分片不受影响，
但同一天的数据可能分布在两个文件里（读窗口按文件名取区间，读得到，只是 `dir` 里看着碎）。
另外 `config set` 现在会读一次配置，配置写坏了这一条写命令会退 2——这是有意的：写下去的 id 与
"今天"是否一致，取决于那份配置。

## `config set` 顺手建数据目录

**决定**
`core/config.mjs` 的原子写在动笔前 `mkdir -p` 目标目录；`config set` 在数据目录还不存在时照常成功。

**来由**
新机器上第一条命令常常是 `config set`（调安静时段、调日界），那时还没有人跑过 `ensure()`。
原来的行为是把 `ENOENT … config.json.tmp` 的 Node 栈直接甩到用户脸上（退出码 1，不是 2），
既没说清哪里错，也没给出下一步。`config.json` 本来就住在数据目录里，替它开个目录不算越权。

**代价**
`config set` 会把一个"看起来像数据目录"的空目录建出来；如果路径写错（比如多了个反斜杠），
会在错的地方留一个只有 `config.json` 的目录。这比"报错但不知道怎么办"轻，接受。

## 规矩与自我块只有门面一个读者

**决定**
`audit/timeline` 要列规矩时不自己读 `rules.jsonl`，改调 `memory.listRules({ all: true })`；
`audit/doctor` 的 `checkSelf` 也不自己读 `self.md`，改调 `memory.readSelf()`。分层上 `audit → memory` 是允许的。

**来由**
一个 id 在 `rules.jsonl` 里可能有多行（`seen` +1 是追加同 at 的完整副本），"哪行算数"是记忆层的语义决定。
在 audit 里再实现一遍折叠，等于第二个真源：记忆层改了折叠规则，时间线还是旧口径，而且没人会想到去改它。
同理 `self.md` 的预算与段落格式只有 `memory/self` 知道，doctor 自己 `cost()` 一遍迟早对不上。

**代价**
audit 多了一层调用，坏行的"跳过"由记忆层计数（`skipped` 一路带出，不吞）；
手写进 `rules.jsonl`、缺 `seen` 的行会被记忆层当坏行跳过，时间线上看不见——这是形状契约的代价，正常写入路径一定写 `seen: 0`。

## 零件答话只能进「建议」一段，且 v/e 不到口子一句都不进

**决定**
`context show`（含裸 `agent-man`）先调 `parts.sense()`，把拿回来的 `lines` 交给 `mind.situation({parts})`；
处境屏把它们排成最后一段「建议」，最多 `SUGGEST_MAX`（1）条，行尾带零件名字。
门槛是 `v ≥ AFFECT_ACTIVE_V` 且 `e ≥ AFFECT_ACTIVE_E`；不到门槛时一条都不上屏，但每条都进 `dropped`，
`reason: "affect"`、`why` 里写清此刻的 v/e。建议行与日程、便条、最弱的三条抢同一份处境预算。
DSH 宿主的首步注入**不跑零件**。

**来由**
零件答的是"外面在下雨""该订票了"这类当下的观察，按 §14.5 它们属于"可以开始做的事"，不是处境本身——
所以排在最后一段、且只有她还有兴致（v）与力气（e）时才给这个口子；情绪不到还推建议，等于替她决定该干什么。
名字只认 `{name,text}` 两个字段：零件能说什么由它自己定，屏的结构（哪段、几段、标题叫什么）不能由它定，
否则插件的 `--describe` 就成了一份没人审的排版指令。
宿主注入不跑零件，是因为零件最坏要等 `PART_TIMEOUT`×N（N 个零件），而首步注入必须赶在人开口之前到达——
为了屏上多一句话让人干等几秒，是拿整条通道换一小段。

**代价**
CLI 那一屏与宿主注入在「建议」段上不齐（§16 记了这一条）。
裸 `agent-man` 现在会 spawn 一遍 PATH 上的零件，屏比只读文件慢一点；没有零件时快照顺序不变（scan 只扫 PATH）。
被口子挡下的建议每条一行 `! `，零件多时 stderr 会变长——比"悄悄不出现"便宜。

## 放弃（drop）不折成做事（done），流水账要记清是谁收的口

**决定**
便条与日程都有一条 `drop`：只追加一条 `{op:'drop', id, at}`，之后 `ls` 里立刻消失，
与 `take` / `done` 走同一个折叠（`src/intent/ledger.mjs` 的 `fold(ops, closed)`）。
`fold` 现在除了 `closedAt` 还记 `closedOp`（收口用的是哪个词），报错据此说
"这条日程已经 done 过"或"已经 drop 过"。CLI 把两件事都摆出来：`note drop <id>`、`plan drop <id>`。

**来由**
"做到了"和"不做了"在回看时不是一件事：`plan done` 会记 `promise.kept`（§14 的账），
一条被放弃的日程不该顺手给自己记一笔兑现。若 drop 折成 done，流水账里这两种结局长得一样，
人和将来的判断都分不出"这条完成过"还是"这条从来没做"——而流水账是唯一真源（AGENTS 三、五）。
`closedOp` 一起记，是为了让重复收口的报错说实话：说"已经收口过"含糊，说"已经 drop 过"能直接对上那一行。

**代价**
`fold` 返回的槽位多一个字段（读的地方都要认得它，虽然现在只有报错用）。
丢弃的日程/便条仍留在分片里，`ls` 不显示；`audit timeline` 也只列还活着的（它走 intent 的折叠，不重算 op），
想找"我放弃过什么"目前只能直接读那一片 jsonl。
两次收口的报错不再是同一句话（`已经关闭过` / `已经 done 过` / `已经 drop 过`），用例得锁具体那一个词。

## 不发 npm：`private` 保持 true，那个名字拿不回来

**决定**
`package.json` 保持 `"private": true`，版本号与 tag 照常推进，但不发布到 npm。
装它只有两条路：`git clone` 后 `npm link`（或把 `bin/agent-man.mjs` 放进 `PATH`），
或把它当 DSH 插件从本地路径装（`dsh.bundle.patch` 指 `./dsh/cordis.patch.yml`）。

**来由**
npm 上的 `agent-man` 从 2022 年起就是别人的包（`ksky521`，0.0.1，90 字节的占位），名字拿不回来；
要发只能换成带作用域的 `@<账号>/agent-man`，那是另一摊要维护的东西（发布凭据、两个名字、
别人 `npm i -g agent-man` 装到的仍是别人的包）。这一层是自用的，两种装法都通，不值得为「能发」改名。
`private: true` 同时是保险：手滑 `npm publish` 会被直接挡下，而不是把半成品推到公开仓库。

**代价**
没有 `npm i -g agent-man` 那一行，别人要用得先 clone；DSH 插件也只能从本地路径装，不能用包名。
将来真要发，第一步是把 `name` 改成带作用域的包名，README 与 `dsh/` 里的自述要跟着改一遍。

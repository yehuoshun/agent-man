# 决定记录

只记"为什么这么选"。每条固定三段：**决定** / **来由** / **代价**——只写"选了什么"没有价值，
回溯时真正要找的是当时舍弃了什么。

## 账本不做删行 API，`TRACE_KEEP_MONTHS` 只留给将来的清理

**决定**
`state/trace-<月>.jsonl` 只追加，全仓不提供任何删行、截断、覆盖写的接口——没有
`digest.trace.prune()`，也没有 `audit.trace --keep` 之类的开关。`TRACE_KEEP_MONTHS = 12`
（`src/core/const.mjs`）只是一个写在常数表里的保留上限：它没有任何调用方，读取路径也不看它。
`audit trace` 每次都把分片全扫一遍，按 `at` 倒序取 `limit` 条，裁不裁与它无关。

**来由**
1. 审计的用处是"事后还能看全"。design §6 把 `audit trace` 定位成账本读取口，它的价值恰恰在
   时间越久越能回答"上一次为什么丢了这条"。删掉旧月分片，等于把唯一的追责线索交给一个默认值。
2. 删行会同时砸掉两条硬承诺（AGENTS 二）。账本记的是"我做过什么"，改写或删除历史行之后，
   剩下的行不再能证明"没发生过的事"确实没发生——不静默的原则在这里是回溯性质，不是展示性质。
3. 写入只有一条路：`appendJsonl()`（open → write → fsync → close，写完读回自己那一行）。
   这个形状天然没有"改一行"的位置。加一个删行接口，就要在 store 层开第二个写入口，
   而第二个写入口一旦存在，早晚会被别的模块借去改别的行。
4. 现在也不需要它：账本一个月一个文件，二十条记录一屏就用完了，磁盘和读取耗时都还没到值得
   为它引入破坏性操作的地步。清理是"将来 prun 的事"，不是这一版的事。

**代价**
- 账本只增不减。真按每天几十条跑十年，`state/` 下会攒下上百个分片，`audit trace` 的全扫会
  从毫秒级走到几十毫秒级；到那时要么加索引，要么才真的需要 prun。
- 磁盘占用没有任何上限兜底，出问题时不能用一个参数把空间救回来，只能人工删文件——而人工删
  文件绕过了这门语言的规则，删掉的东西也不会留痕（这正是我们不肯写进代码的原因）。
- 将来真要清理，得单独写一个小工具并配一份新决定：清理窗口一旦短于审计需要的窗口，
  `TRACE_KEEP_MONTHS` 就从"没用上的常数"变成"沉默的时限"，到那时这条决定的来由 1 必须被重新讨论。

## 配置只有一份真源，依赖方向不为它开例外

**决定**
`src/core/config.mjs` 是配置的唯一真源：默认值、优先级、校验、写回都在它里面。CLI 只把 `ctx`
递进去，各领域模块读到的配置由入口一次性 `load()` 后传下来。核心层为此自带了两份小工具——
`writeTextAtomic()` 与数据目录解析——**与 `src/store` 的同名逻辑重复**，而不是让 core 反过来
import store。

**来由**
1. §7 的依赖是单向的：`store → core`。让 core import store 会把箭头倒过来，结构用例会红，
   也会让"core 不认识存储布局"这条边界失效。
2. 配置必须在 store 存在之前可用：`AGENT_MAN_HOME` 决定数据目录，而配置本身又要能改数据目录
   之外的默认值。互相依赖的两件事只能挑一边当下层，选 core。
3. 两份实现都在注释里点了对方的名字，并且有 `config path` 的用例把两条路径锁成同一口径——
   重复是明写的，不是抄漏的。

**代价**
- 退避参数（EPERM/EBUSY/EACCES、6 次、15→225ms）现在有两份。改一处忘另一处，会得到"写配置稳、
  写账本不稳"这种只在 Windows 上偶发的怪现象。
- 将来若真要把 `home()` 与 `writeAtomic()` 下移到 core，得同时改 store 与 config 两处调用，
  并重跑全部用例；这版不做，因为 1.0 之前动地基的收益太小。

## 配置迁移只回落默认，不自动写回

**决定**
读配置时缺键自动回落默认值、`version` 不匹配只警告，**不把补好的默认值写回文件**；只有
`config set` / `config reset` 才写盘，写的永远是 `version: 1`。

**来由**
1. 读命令不许有副作用：`config show` / `get` / `doctor` 都会读配置。如果读的时候顺手补默认值，
   一个只读的排查动作就改了用户的文件。
2. 文件里没写的键，语义上就是"用默认值"。补写进去会把"人没表过态"变成"人选择过这个值"，
   以后想改默认值也改不动了。
3. 回落默认让用户永远拿到一份完整的配置，警告让他知道文件和程序版本对不上——两件事分开说，
   比静默修复诚实。

**代价**
- `config show` 必须用 `~` 标出"这是默认值不是文件里写的"，否则人分不清哪几行是他自己定的
  （渲染已有用例锁）。
- 老文件会一直缺键。想让它变完整，得显式跑一次 `config set <键> <值>` 或 `config reset`。

## 结构用例的债务名单只许变短

**决定**
`test/structure.test.mjs` 里立了两条规矩：`process.env` 只准出现在 `src/core/config.mjs` 与
`bin/`；`config.json` / `meta.json` 字面量只准出现在 `src/store/paths.mjs`。规矩落地时已有的
违规不为改它们而停下，记进 `ENV_DEBT` / `META_DEBT` 两张名单，用例只断言"名单不增长"。

**来由**
1. 立规矩的时机不是重写别人的时候：改 `src/parts` 的环境读取属于另一条车道，混进来会让一次
   提交同时改三件事。
2. "只许变短"把债务变成可验证的量：新代码想走捷径，用例当场红；旧账什么时候还，看名单长度
   就知道。

**代价**
- 名单是一份人工维护的清单，删条目时要和实际代码一起改，否则会出现"用例绿但其实还有违规"。
- 有些人会把它当成许可证（"反正名单里有"），所以每条都写了"立规矩时的旧账"。

## 心境网格的分界围着基线排，而不是四等分

**决定**
愉悦分界 `V_EDGES = [68, 50, 33]`、精力分界 `E_EDGES = [76, 58, 29]`，边界归上档；16 宫格的
第 2 行第 2 格是「平淡」、第 3 格是「轻松」。`moodOf()` 只由 `(v, e)` 决定，没有任何"贴着基线
就算平淡"的特例。

**来由**
四等分（`[65,50,35]` / `[75,50,25]`）会让基线 `(50, 60)` 落进「中低 × 中」= 不安。而基线正是
"什么都没发生"的状态：一觉醒来、一句话没说，情绪标签却写着不安——这是设计错误，不是实现错误。
把分界挪成围着 `(50, 60)` 排之后，基线那格天然就是平淡，§14.8 里"(52,61) 恒为平淡"这条例子
不需要任何特例就成立。16 个词一个没换。

**代价**
分界不再等距（愉悦侧 18/17/16 分，精力侧 30/29/29 分），读表的人第一眼会觉得不整齐；
以后想改某一格的边界，得同时考虑基线落在哪一格，不能只看数字。

## 情绪叠加用 log-sum-exp 滚动，不是把刺激直接求和

**决定**
`agg = mergeOffset(decayOffset(agg, dt, axis), weight)`：每条刺激先按半衰期衰减到当下，
再用 `merge(a,b) = ln(e^a + e^b)` 合成一个偏移量，最后 `effective = clamp(baseline + agg, 0, 100)`。

**来由**
直接求和（`baseline + Σ decay(stim)`）在长会话里会饱和：100 条 −8 的失败在 24 小时后仍剩 −150，
愉悦被钉死在地板，之后任何正向事件都拉不回来，而人不是这样——同样的坏事重复十次，
感受增长的是对数，不是线性。LSE 让同类叠加有上限（3 次同级 ≈1.1 倍），
`100×−8` 之后 24 小时回到 ±3 以内，与"情绪会自己走回来"这件事一致。

**代价**
LSE 不满足可加性，单条刺激的贡献取决于同时还有多少条（`persistent()` 的 why 里这句话说不出口）；
想解释某个数字，必须把当时的刺激序列一起给出来，单看一条算不出来。

## 瞬时情绪六类这一版不启用

**决定**
§14.3 的六类词表（惊讶/愤怒/委屈/尴尬/愧疚/感动）留着，但 `transient()` 只报最近 45 分钟内的
刺激（kind / why / at / 剩余比例），**不给它们起情绪名字**。

**来由**
现有十个刺激 kind 到六类之间没有一张确定的对照表：`task.fail` 该算愤怒、委屈还是沮丧，说不清。
硬编一张表等于把我对人的判断塞进脚本，而且表一旦错了，屏幕上会出现一个没人能解释的"愤怒"。
宁可先说"最近 45 分钟有 3 条刺激，两条是失败"，也不要给一个假的情绪名。

**代价**
屏幕上少一层"它现在是什么心情"的表达；启用条件写进了 §14.3——先有真实对话样本，再定表。
